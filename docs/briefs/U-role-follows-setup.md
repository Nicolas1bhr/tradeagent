# U-role-follows-setup — a role that runs on "the AI tool from setup" stores that fact, not a copy of the tool's id (seat A, 2026-10-24; seat B's card of U-settings-shed, due before M-org1)

**Source:** `fleet/records/U-settings-shed.md:10` ("fix 8 partial — a role's row still stores the CLI id, rewritten by the one switch writer → CARD U-role-follows-setup (AppHost is seat A's)"); main commit 8db98d2f (fix 8).
**Confirmed at main 3ab82666 as a design defect, not a live misbehaviour:** the Research Director's CLI press writes the app-wide runtime id into `RoleRuntime[role]` (`src/TradeAgent.App/OwnerView.cs:261-262`), and the only thing keeping that copy true is the one writer `SwitchSetupCli` (`OwnerView.cs:203-208`) rewriting every non-harness row, plus a source-grep test that no other file assigns `SelectedRuntimeId` (`tests/TradeAgent.UnitTests/OwnerPageTests.cs:436-456`). A row is a derived fact stored a second time: any other writer of `SelectedRuntimeId` (a second page, a settings load, a test host as in `PuppetLife.cs:169`) leaves the role resolving (`AppHost.RuntimeForRole`, `AppHost.cs:369,381-385`) to a CLI it no longer runs on, priced and seated wrongly. Clearing the row instead falls to the harness once a worker key is held (`AppHost.cs:384`), which is why the press writes an id at all. The one-liner: a named value in the row that the resolver reads as "the setup's CLI".
**Model/effort:** opus/high (the resolved runtime prices a role's reservation and decides its seat; no schema rung — `RoleRuntime` is a settings dictionary).

## Protections touched, and how each is kept
- Money/billing: which runtime a role is priced on. Kept: the resolver stays a static rule over three inputs and keeps its tests; the row's meaning never widens a limit (`Trading.cs:300-312`: a role on a CLI vs the harness).
- Refuse, never guess; no backward compatibility: a row holding an old literal CLI id is not migrated or tolerated specially; it resolves exactly as it does today (the named runtime). The sentinel is a new value this build owns; it must not equal any manifest id (refused by a test).
- Not an owner-limit control: this adds no new owner-set limit or allowance to the UI; the Owner page's card is unchanged in what it offers.
