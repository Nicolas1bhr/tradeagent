## Why it exists

GitHub CI (windows-latest) on 3931c10 failed one test, `CoidWitnessTests.The_file_is_never_absent_while_it_is_being_rewritten`
("the temporary file was left behind"): a rename of the temp onto `coid-witness.json` had failed under a concurrent
reader on a contended runner. The same commit passed on the ATAS box and on macOS, and the next CI run passed — a
load-dependent race. The builder established from source what that meant: `Save()` retried only `IOException` for 60 ms,
`UnauthorizedAccessException` escaped on the first attempt, `Submitting` swallowed everything (`MarkWriteFailed`), `Place`
wrapped it in `Guard(...)` and continued to ATAS, and **`EnsureLoaded` never read the temp** — so a claim whose rename
failed lived only in a file no reader opened, and the durable answer to "did this product submit this identifier" was NO
for an order handed to ATAS microseconds later. That is the rule-1 defect; the leftover `.tmp` was the symptom.

**Round 1 (a159bf4).** Rename seam made injectable; retry `IOException` and `UnauthorizedAccessException` (5 attempts,

### Item 1 — the superset rule is MEMBERSHIP, not count (commit `6e9027c`)

**What was actually wrong at `a8b3fb0`.** Round-4 item 5 (`fc91771`) had already replaced the bare
count comparison with `KeepsCommittedRecords`, so the sentence "it compares counts" was no longer
literally true — but the hole it names was still open, one step along. `KeepsCommittedRecords` skipped
a LEADING RUN of committed identifiers unconditionally, on the argument that `Trim` drops the oldest
off the front. `Trim` only removes at the cap. So a candidate under the cap that dropped the first
committed claim and added one of its own passed the check, and adoption dropped the claim, because
the adopted set is what the next save commits.

**RED first.** Verified by running
`dotnet test …IntegrationTests… --filter "…A_candidate_that_swapped_a_committed_claim_for_another_is_ignored"`
at `a8b3fb0` + the new test:

```
Assert.Equal() Failure: Collections differ
Expected: ["TA-1", "TA-2", "TA-3"]
Actual:   ["TA-2", "TA-3", "TA-SWAPPED"]
```

Three records against three, perfect lineage, and `TA-1` was silently dropped.

**The fix.** `KeepsCommittedRecords` → `DropsACommittedRecord(candidate, committed)`, an instance
method (it needs `_cap`) returning the identifier that would be lost, or null. Membership over the
committed identifiers; the missing-prefix allowance is now conditional on the candidate being FULL
(`i > 0 && candidate.Records.Count < _cap` → refuse), because `Trim` removes nothing below the cap.
The "may never shrink the record set" rule is kept as the first check, unchanged in effect. The
rejection line names the identifier instead of printing "3 records against 3", which is the sentence
that made this invisible.

**GREEN.** Verified by running `dotnet test TradeAgent.sln` → 75 / 111 / **198** = 384, 0 failed.

**Mutants (source restored from a `cp` copy each time, then `touch`ed; sha of the copy
`0ad2cd11f89841ae24c5bd5b16895a49e3a99778`):**

| # | Mutant | Result |
|---|---|---|
| M1 | membership body replaced by `return null` — the count check alone | RED: `A_candidate_that_swapped_a_committed_claim_for_another_is_ignored [FAIL]` (1 failed / 76 passed) |
| M1b | the cap condition removed (`if (false)`) — the `a8b3fb0` prefix rule | RED: same test (1 failed / 76 passed) |
| M1c | the trim allowance removed (`if (i > 0)`) — too strict | RED: `A_rewrite_that_trimmed_the_oldest_at_the_cap_is_still_adopted [FAIL]` (1 failed / 76 passed) |

M1c is the both-directions half: the rule refuses a swap AND still adopts the legitimate rewrite that
trimmed at the cap. A tightening that broke recovery on every full witness would fail loudly.

**§9.9 — could a test class or gate catch "compared a count where a set was meant" next time?**
A gate, no: `.Count` in a comparison is everywhere and a lint for it would be noise, and the defect
here was not even a bare count — it was a membership check with an unbounded escape hatch, which no
textual rule distinguishes from the correct one. A TEST CLASS, yes: adoption wants a table-driven
suite over candidate/committed shapes — drop-one, add-one, **swap-one**, hole-in-the-middle,
duplicate, at-cap, under-cap — asserting the committed identifier SET survives in each. The swap row
is precisely what a count cannot express, so its absence from the table is visible in a way its
absence from a bool is not. The cheap general form of the same rule, and the one worth carrying into
review: **when the rule is about a set, the assertion names the members, never the size.** Not built
(item 6 is a LOW batch); recorded for the manager.
